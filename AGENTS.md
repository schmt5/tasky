# AGENTS.md

Guidelines for AI coding agents (and humans) working in this repository.

## About this project

LearningLine (codebase name `tasky`) is a learning and exam platform for
schools, built with Phoenix LiveView. Teachers author learning units and exams
in a Tiptap editor, learners answer in the browser, teachers correct, grade and
export PDFs. Start with [`README.md`](README.md) for setup and
[`ARCHITECTURE.md`](ARCHITECTURE.md) for the context map, the document model and
the grading model.

- Domain code lives in `lib/tasky/`, the web layer in `lib/tasky_web/`, the
  editor (React + Tiptap, TypeScript) in `assets/js/react/`, the PDF template in
  `priv/typst/`.
- The UI is German. Write user-facing text in German with Swiss spelling (`ss`,
  never `ß`). Identifiers and commit messages are English; comments and docs
  are English or German — follow the surrounding file.

## Workflow

- Run `mix precommit` before you are done and fix everything it reports. It is
  identical to CI (`.github/workflows/ci.yml`): warnings as errors, format
  check, `credo --strict`, `sobelow`, `dialyzer`, tests with a coverage gate,
  the TypeScript check, the asset tests and the asset build. Keep the alias and
  the workflow in sync.
- The developer's dev server usually holds the `_build/dev` lock. Compile and
  test with `MIX_ENV=test` instead of stopping it.
- Local Postgres listens on **port 5433**, the app on **4001**. Local logins:
  `mix run priv/repo/dev_users.exs`; a demo course:
  `mix run priv/repo/demo_course.exs`.
- Commits follow Conventional Commits with a scope (`feat(exams): …`,
  `fix(tasks): …`) and carry `Signed-off-by` (`git commit --signoff`). Commits
  are not GPG-signed.
- Use `Req` for HTTP. Do not add `:httpoison`, `:tesla` or `:httpc`, and do not
  add dependencies without being asked.

## Project rules

These are invariants. Breaking them loses teachers' work or leaks data, often
without anything visible on screen.

### Production has live data

Real courses, units and exams are in production, and migrations run on boot
(the `Ecto.Migrator` child in `Tasky.Application`) while the old release still
serves requests.

- A change that alters what stored data means needs a migration that
  **converts existing rows** (SQL `execute` in `up`, a sensible `down`).
- Dropping or renaming a column the running code still reads takes **two
  deploys**: first stop using it, then remove it.
- Additive changes (new nullable columns, new JSON keys with a nil/false
  default) need nothing special.
- Generate migrations with `mix ecto.gen.migration name_with_underscores`.

Rule changes are different: when a scoring rule changes, the new rule may
simply apply to old exams. What must survive is every value a teacher typed by
hand (manual verdicts, part points).

### Authorization goes through scopes

- Context functions take the `%Tasky.Accounts.Scope{}` as their first argument
  and authorize internally (`Tasky.Policy`). Never authorize only in the
  LiveView.
- `:system` is the trusted scope for supervised background jobs. Never pass it
  from the web layer.
- Ownership: owners manage their courses, units and exams, admins everything.
  Organization: teachers of one organization share its classes and learners.
  The policy fails closed — no organization means no visibility.
- `role`, `organization_id`, `class_id`, `user_id` and similar fields are set
  programmatically, never cast from params.

### One document, three renderers

Units and exams are stored as Tiptap JSON. The React editor renders it for
teachers, `TaskyWeb.ExamDocHTML` renders the learner's answer sheet, and
`priv/typst/tiptap.typ` renders the PDF. **A new node or mark needs a branch in
the editor, in `ExamDocHTML` and in the Typst template.**

The teacher authors content and sample solution in one document;
`Tasky.Correction.AnswerKey` splits it into the answer-free `content` and a
`sample_solution` map keyed by each field's `answerId`. Learners must never
receive the sample solution.

### Grading

- `block_verdicts` accepts exactly `"correct" | "wrong" | "half"` (legacy) |
  a number | `nil`, keyed by `answerId` — for **every** writer, including the
  auto-corrector.
- Auto-correction never overwrites a teacher's verdict:
  `auto_block_verdicts` records what the auto-corrector last wrote, and a block
  whose verdict differs from it belongs to the teacher.
- Grading math lives in `Tasky.Grading` (pure). Round **before** clamping.
- When you add a verdict writer or touch grading math, add a case to
  `test/tasky/exams_auto_correction_test.exs`.

### Prefer teacher control over heuristics

When a value is something the teacher knows better than the system (how much
space an answer needs, how many points a question is worth), give the teacher
a control for it. A heuristic may supply the starting value, never the final
one.

## Routes and authentication

Auth is generated by `phx.gen.auth` and assigns `@current_scope`, never
`@current_user` — use `@current_scope.user`. Pass `current_scope` to
`<Layouts.app>`. Add a route to the `live_session` of the role that uses it,
and tell the user which scope and `live_session` you chose and why.

| `live_session` | Path | Who | Pipeline / hook |
|---|---|---|---|
| `:tasks` | `/` (courses, units, exams, classes, students, catalog) | teachers and admins | `:require_admin_or_teacher` |
| `:student` | `/student` | learners | `:require_student` |
| `:admin` | `/admin` | admins | `:require_admin` |
| `:guest` | `/guest` | exam guests via token, no account | rate limit, `:mount_current_scope`, SEB guard |
| `:require_authenticated_user` | `/users/settings` | any signed-in user | `:require_authenticated` |
| `:current_user` | `/users/register`, `/users/log-in` | anyone | rate limit, `:mount_current_scope` |

- The plug pipeline and the `on_mount` hook must check the same role: a
  `live_redirect` within a `live_session` never passes through the plugs again.
- A `live_session` name is defined once; add routes to the existing block.
- Controller routes go into a scope with the matching plugs (`/api`,
  `/api/student`, `/api/guest`, `/uploads` and `/share` each have their own
  pipeline).
- A `scope` aliases its module prefix: inside `scope "/admin", TaskyWeb.Admin`
  write `live "/users", UserLive`.

## UI conventions

- Write your own Tailwind components. daisyUI is loaded, but use it only for
  the modal and tooltip primitives below.
- **Modals:** `<dialog class="modal modal-open">` with a
  `<div class="modal-box">` and a `<div class="modal-backdrop">`, guarded by
  `<%= if @show_modal do %>`. Close on `phx-click="close_modal"` (backdrop) and
  `phx-window-keydown="close_modal" phx-key="escape"`, and reset all modal
  assigns on close. See `lib/tasky_web/live/task_live/progress.ex`. The
  `<.modal>` component in `core_components.ex` is a different (JS show/hide)
  pattern — don't mix them, and never build modals from `fixed inset-0` divs.
- **Confirmations** use such a modal, never the native `data-confirm`.
- **Colour:** red is only for actions that destroy data. Reversible
  confirmations use the normal sky primary button.
- **Tooltips:** never the HTML `title` attribute. In HEEx use the daisyUI
  `tooltip` + `data-tip` pattern (see `back_button` in `core_components.ex`), in
  React the Radix tooltip (`Tip` in the editor toolbar).
- **Icons:** the `<.icon name="hero-…" />` component, never `Heroicons` modules.
- Give key elements (forms, buttons, list items) unique DOM ids; tests select by
  them.

### CSS and JS

- Tailwind v4, no `tailwind.config.js`. Keep the import header of
  `assets/css/app.css` (`@import "tailwindcss" source(none);` plus the
  `@source` lines). Never use `@apply`.
- Only the `app.js` and `app.css` bundles exist. Import vendor code there; no
  external `<script src>` or `<link href>` in layouts, no inline `<script>`.
- Scripts inside HEEx are colocated hooks:
  `<script :type={Phoenix.LiveView.ColocatedHook} name=".MyHook">`, names start
  with a dot. External hooks live in `assets/js/hooks/` and are registered in
  `app.js`.
- A hook that manages its own DOM also needs `phx-update="ignore"`, and every
  `phx-hook` element needs a unique id.
- React islands are mounted through hooks (`create_react_hook.jsx`); see
  `docs/REACT_INTEGRATION_GUIDE.md`.

## Phoenix and LiveView

- LiveView templates start with
  `<Layouts.app flash={@flash} current_scope={@current_scope}>`. `<.flash_group>`
  may only be called inside `layouts.ex`.
- Use `<.link navigate={…}>` / `<.link patch={…}>` and `push_navigate` /
  `push_patch`; never `live_redirect` / `live_patch`.
- Avoid LiveComponents unless there is a specific need.
- Name LiveViews with a `Live` suffix (`TaskyWeb.ExamLive.Show`).

### Forms

- Build the form in the LiveView with `to_form/2` and render
  `<.form for={@form} id="…">` with `<.input field={@form[:field]} />` for every
  input, select and textarea. Never pass a changeset to `<.form>`, never use
  `let={f}`, never access the changeset in the template, never use
  `Phoenix.HTML.form_for`.
- Raw `<input>`/`<textarea>` outside a `<.form>` do not send `phx-change` /
  `phx-submit` correctly.
- In a modal keyed per record, include the record id in the form id
  (`id={"feedback-form-#{@student.id}"}`) so LiveView re-renders it.
- Read submitted values by pattern matching the `:as` key:
  `def handle_event("save", %{"feedback" => params}, socket)`.
- Overriding `<.input class="…">` drops all default classes; style it fully.

### Streams

- Use streams for collections: `stream/3`, `stream(…, reset: true)` to refilter,
  `stream(…, at: -1)` to prepend, `stream_delete/3`.
- The parent needs `phx-update="stream"` and an id; each child uses the stream's
  id: `<div :for={{id, item} <- @streams.items} id={id}>`.
- Streams are not enumerable and have no count: track counts in an assign, and
  render an empty state with `class="hidden only:block"` as the only sibling.
- When an assign changes what a streamed item renders, re-insert the item.
- Never use `phx-update="append"` / `"prepend"`.

### Hooks and events

- `push_event/3` returns a socket — rebind or return it. Hooks receive it with
  `this.handleEvent`; `this.pushEvent(event, payload, reply => …)` pairs with
  `{:reply, map, socket}`.

### HEEx

- `~H` / `.heex` only. Interpolate with `{…}` in attributes and for values in
  bodies; use `<%= … %>` for block constructs (`if`, `case`, `cond`, `for`)
  in bodies.
- There is no `else if` — use `cond` or `case`.
- Class lists use list syntax: `class={["base", @flag && "x", if(@y, do: "a", else: "b")]}`.
- Generate content with `<%= for … do %>` or `:for`, never `Enum.each`.
- Comments: `<%!-- … --%>`.
- Literal `{` / `}` (code samples) need `phx-no-curly-interpolation` on the
  parent tag.

## Elixir and Ecto

- Lists have no index access (`list[i]`); use `Enum.at/2` or pattern matching.
- Rebind the result of `if` / `case` / `cond`; rebinding inside the block is
  lost.
- One module per file. Structs have no Access behaviour: use `struct.field`,
  and `Ecto.Changeset.get_field/2` for changesets.
- Never `String.to_atom/1` on user input.
- Predicates end in `?` and don't start with `is_` (that's for guards).
- Dates and times: the standard library (`Date`, `Time`, `DateTime`).
- `Task.async_stream/3` for concurrent enumeration, usually with
  `timeout: :infinity`. Named OTP processes (`Registry`, `DynamicSupervisor`)
  get their name in the child spec.
- Preload associations the template uses.
- `Ecto.Schema` fields use `:string` for text columns too.
  `validate_number/2` has no `:allow_nil`.

## Tests

- Test outcomes, not implementation. Select elements by their DOM ids with
  `element/2` and `has_element?/2` instead of matching raw HTML or text.
- Drive forms with `render_submit/2` and `render_change/2`.
- Start processes with `start_supervised!/1`. No `Process.sleep/1` or
  `Process.alive?/1`: monitor and `assert_receive {:DOWN, …}`, or call
  `:sys.get_state/1` to sync.
- Debug selectors with `LazyHTML.from_fragment(render(view))` and
  `LazyHTML.filter/2` instead of dumping the whole page.
- Run one file with `mix test path/to/test.exs`, failures again with
  `mix test --failed`.
